"Trust the data" sounds like one thing but it's actually several separate questions, and this project touches almost all of them. Worth pulling them apart, because a dataset can be trustworthy in one sense and not in another.

**1. Trust that the raw data is what it claims to be**
Before any statistics: are `pickup_datetime`, `trip_distance`, `pickup_borough` correct and consistently defined? Are there duplicate trips, impossible values (negative duration, zero distance with 40 minutes duration), or a units mismatch somewhere upstream? None of the diagnostics in this project test this directly — Breusch-Pagan and Jarque-Bera assume the values are correctly recorded and just check the *shape* of the errors. If there's silent corruption in the source data, every downstream test inherits it invisibly. This is usually the weakest-checked layer and the one worth a deliberate pass if it hasn't happened yet.

**2. Trust that the sample represents what you're generalizing about**
This is where the borough imbalance matters directly: Manhattan n≈155K vs Staten Island n=84. You can trust the Manhattan mean far more than the Staten Island mean, not because of any flaw in the data, but because 84 points just can't pin down a population parameter tightly — CLT convergence at that n is genuinely weaker. "Trust" here isn't binary; it's a confidence interval question, and the project handled it correctly by treating small-group findings more cautiously (Kruskal-Wallis as a cross-check) rather than reporting Games-Howell results with the same confidence across all boroughs.

**3. Trust that a test's own assumptions hold before trusting its conclusion**
This is the through-line of the whole stats track. A p-value is only trustworthy if the test producing it is valid for the data it's being run on. Two examples already in this project:
- Breusch-Pagan and Jarque-Bera are valid on the OLS residuals as computed — but their *p-values* aren't the point at n≈200K; a p≈0 there is nearly guaranteed regardless of practical severity. Trust comes from the effect size (kurtosis=25.5, 6.3→21.4 std spread), not the p-value.
- Durbin-Watson computed on randomly shuffled rows is the clearest case of *not* trusting a number: the test's validity depends on row order carrying temporal meaning, and it didn't. DW=1.994 isn't wrong, it's answering a different question than the one being asked. That's why it's flagged as a caveat, not a finding — a number can be arithmetically correct and still not support the claim you want to make with it.

**4. Trust that a model's estimates and its uncertainty are both valid**
Heteroskedasticity doesn't bias OLS coefficients — you can still trust the point estimates. But it does bias the standard errors, so you *can't* trust the p-values or confidence intervals without correction (HC3 in script `09`). This is a subtle distinction worth keeping straight: "the model is somewhat trustworthy" isn't a single yes/no, it's trustworthy for some outputs and not others.

**5. Trust that there's no leakage**
This is forward-looking but critical: if any engineered feature encodes information that wouldn't be available at prediction time (or literally encodes the target), `12`'s LightGBM metrics would look great and mean nothing. This is why the leakage pass matters — it's not a nice-to-have, it's a precondition for trusting *any* performance number that comes out of that script.

**6. Trust that a result is stable, not an artifact of one split or one sample**
The random-vs-time-based split issue is this exact concern: an OLS R² from a random split and a LightGBM MAE from a time-based split aren't comparable, because they're answering "how well does this fit a shuffled sample" vs "how well does this predict the future given the past" — different questions that happen to produce numbers in the same units. Trusting a comparison requires the same evaluation regime, which is why that's flagged as a gap rather than glossed over.

**The common thread**
In a project like this, "trusting the data" mostly isn't about the data being wrong — it's about matching each claim to the specific thing the test, sample, or model actually validated, and not letting adjacent-looking numbers (a DW statistic, a p-value at large n, an R² from a different split) borrow credibility they haven't earned. The discipline in this handoff — flagging DW as invalid, treating small-n Shapiro results skeptically, refusing to compare `08`/`09`/`11` against `12` directly — is exactly what earning that trust looks like in practice: it's earned incrementally, by scoping each conclusion to what was actually tested, not assumed wholesale from "we ran the numbers."
